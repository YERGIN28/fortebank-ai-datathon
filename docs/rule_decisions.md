# Финальный вердикт и подключение

Расширение от 18.10.2026: кроме ухода кассира добавлены две условные проверки
по п. 20 № 231; п. 42 оставлен только для проверки человеком. Полный перечень
условий и ограничений: [покрытие правил](rule_coverage.md).
Для трёх типов condition_checks теперь формирует дополнительный публичный метод
`QwenModel.check_cash_rules_context()` через `app.rules.context.enrich_service_context`.

`app.rules.decision.decide_video(result)` принимает словарь `InferenceResult.to_dict()`.
`build_job_result(job_id, result, extract_frame)` формирует публичный ответ backend.
Callback `extract_frame(seconds)` читает исходное видео и возвращает
`{"timestamp_sec": ..., "image_base64": ...}`. Загруженный файл удаляется после этого вызова.

Результаты:

- `done / violation`: есть событие с проверенным нормативом и видимыми условиями.
- `done / no_violation`: полный проход, нет подтверждённых или нерешённых событий.
- `failed / error`: неполный проход, неправильные данные, неизвестное событие,
  непроверенное правило, недостаточно контекста или ошибка извлечения доказательств.
  Поля `verdict` у ошибки нет.

Внутренний `check_events()` сохраняет кандидатов `needs_review` для диагностики.
Они не являются результатом для жюри. `evaluation.run_rules.process_video()` теперь
вызывает финальное решение; поле `candidates` остаётся только в диагностическом CLI.
Список `violations` у `decide_video()` внутренний: вместо JPEG он содержит секунды.
В API передаётся исключительно результат `build_job_result()`.

## Первое исполняемое правило

`cashier_leaves_during_service`: пункт 22 Правил, утверждённых постановлением
Правления НБРК от 29.11.2019 № 231.
Официальный источник: https://adilet.zan.kz/rus/docs/V1900019680
Текст пункта дополнительно проверен поиском официальной версии
https://old.adilet.zan.kz/rus/docs/V1900019680/compare.

Два условия: кассир покинул рабочее место и обслуживание клиента ещё продолжается.
Наличные на столе, вставание со стула, высокий confidence и refined сами по себе
не подтверждают эти условия. Не требуется додумывать внутренние процедуры банка.

Каждое условие в `condition_checks` содержит `state` (`observed`, `refuted`,
`unclear`) и `evidence_timestamps_sec` с видимыми доказательствами:

```json
{
  "type": "cashier_leaves_during_service",
  "start_sec": 10,
  "end_sec": 15,
  "description": "Искусственный пример формата, не результат модели",
  "condition_checks": {
    "cashier_left_workplace": {"state": "observed", "evidence_timestamps_sec": [10]},
    "customer_service_ongoing": {"state": "observed", "evidence_timestamps_sec": [15]}
  }
}
```

Оба наблюдаются — событие подтверждается. Есть наблюдаемое опровержение любого
обязательного условия — этот кандидат отклоняется. Недостаточная видимость
остаётся нерешённым случаем. Подтверждённое событие даёт `violation`, даже если
другое наблюдение неизвестно; частичный анализ всегда даёт `failed`.

Обычный `Observation` основного прохода **не содержит** `condition_checks`.
Их передаёт дополнительный локальный просмотр контекста в интеграционной сборке. До него
`cash_left_unattended` и `unauthorized_phone_use` остаются кандидатами;
правило 22 нельзя автоматически применять к любым наличным без присмотра.
Рутинные `cash_*`, `document_*`, `object_transfer` не подтверждают нарушений.

Полный проход с пустым списком наблюдений означает только отсутствие найденных
событий в реализованном анализе, а не доказанную универсальную проверку всех норм.
Качество и частоту `failed` необходимо измерять на реальных видео отдельно.

## Проверки

`python -m unittest evaluation.test_decision -v` проверяет синтетические случаи:
положительный и отрицательный результат, контекст, ошибки, неполноту и доказательства.
Реальное качество локальной модели этими проверками не измеряется.
